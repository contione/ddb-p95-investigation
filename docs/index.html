DynamoDB p95
为什么约每小时抬头？

结论：尖峰期间实际打到 DynamoDB 的查询量平稳，不支持缓存击穿；这条慢请求随后继续执行，也没有证据表明 GetOrSetAsync 死锁。先不改缓存、不加预热，优先查发起查询的请求在凭证 HTTP 前的约 1 秒花在哪里。

01 / 现场证据

凭证刷新是首要调查方向，但还不是 1 秒的归因

用户观察：约每小时出现 p95 高点；慢 trace 是「进服务 → 约 1 s 无 span → 快速访问 /v1/credentials → POST DynamoDB」。上游 200 ms 超时后重试，另一个 pod 在 80–90 ms 内直接发出 POST。测试 pod 的一次 curl 为 257 ms，取回的凭证距过期约 1 小时。以下不是生产测量结果。

观察支持什么不能推出什么
凭证端点在 POST 之前符合 SDK 先取凭证再签名、发请求的顺序。HTTP span 之前可以有业务排队、运行时暂停或漏采。单个 span 不是整次取凭证的耗时。
第二个 pod 快该次重试不需要可见的端点请求，可能已有可用凭证。并非同时同进程的对照；缓存、负载、节点、连接、请求次序都变了。
DDB 流量平稳不支持整片缓存同时穿透并制造大量 DDB 流量。只有观测到同一 pod、同一个 key 的多个请求在等同一次加载，才能把缓存记为放大因素；回源量平稳本身不能证明存在这些等待者。
每小时峰值值得对齐到期、发布、节点作业与资源指标。每个 pod 各自刷新不自然推出所有 pod 整点同步；独立相位通常会抹平峰值。

先定义 p95：上游逻辑请求、每次 HTTP 尝试、服务端请求、仓储页读取、成功 DDB 服务请求是五个不同总体。一个刷新事件要抬升某个桶的 p95，通常需要让约 5% 或更多样本变慢（受样本数、桶宽和插值影响）。例：1000 次里仅 1 次慢，能抬高 max，却不足以单独解释 p95。不要平均各 pod 的 p95。按相同窗口合并 histogram buckets，同时看请求数、超时数和 >200 ms 占比。

03 / SDK 机制

区分刷新发起者、同实例等待者和同 key 等待者

环境变量及路径与 EKS Pod Identity 相符，但更靠前的 provider、profile 或显式凭证可能优先。Agent 运行在节点并缓存凭证；pod 的进程缓存、节点 agent 缓存和 AWS 签发的 Session 不是同一层。不要从“发起一次 HTTP”推出“本次新签发了凭证”。[1] [4] [6]

业务 miss → 进入 factory → 仓储实际读页 → SDK CredentialsRetriever → provider.GetCredentialsAsync → 签名 → DDB HTTP attempt。仅同一缓存实例同 key 共享 factory；不同 key 到此仍可争用同一个凭证对象。[2] [3]

核对的 v3.7 快照：异步入口先 SemaphoreSlim.WaitAsync()；拿到单实例信号量后才检查状态。空状态或超过内部过期时间时，在释放信号量前等待生成新凭证；其余调用积压，交还后重新检查，通常不再发 HTTP。这里的「阻塞请求」指延长临界路径，不等于所有等待者都占着一个线程。同步入口则用 Wait。[2] [3]

该快照的 GenericContainerCredentials 覆写同步生成，基类 async 路径用 Task.Run 调它；生成过程读 token 文件、访问本地端点，失败可抖动重试并 sleep。因此，发起者可能已占信号量、但刷新工作仍在等线程池调度；这能同时产生前置空白和一群慢等待者。不是所有 v3 小版本都已验证。[3] [4]

你这条 trace 的关键矛盾：若它只是等待同一 provider 的另一次成功刷新，轮到它时通常会复用结果，不应再为同一次刷新自己发 HTTP。先查凭证 span 的父子关系、进程和 attempt；若确是它发，优先查发起者的调度、读 token、前序失败/退避或更上游的排队。仅凭“空白后出现快速 GET”无法把 1 秒记在锁上。

容器 provider 在该版本预留 15 分钟，内部有效期为端点返回的 UTC Expiration − 15 min；超过门槛后的首次取用触发。若 12:00 获得有效至 13:00 的凭证，持续有流量时预计约 12:45 后刷新，不是必在 13:00。若 agent 返回同一过期时刻、业务间歇、真实 TTL 不同或节点相位相关，观测间隔还会变化。用前一次生产 Expiration 预测下一次，再比较墙钟整点。[1] [3] [4]

04 / 贴出的缓存

区分第一个慢查询和等待它的请求

重复粘贴的两段相同，按一份评估。命中不会等待 factory；同一实例和 key 的 miss 共用 Lazy 创建的 Task。一旦一次加载慢，所有尚未超时的跟随者都慢，跟随者 trace 甚至可能没有 DDB 子 span。这是可能的放大机制，尚未在线上观测到；它不能解释第一个发起查询的请求为什么慢，不建议据此修改缓存。

  • ExecutionAndPublication 保护的是 Lazy 值的创建。从调用 lazy.Value 到 factory 首次真正异步挂起前，双检、构造查询和 factory 同步前缀可能在创建线程执行，其他同 key 线程在取 Value 时也可能短暂等待。分别计时取 Value 与 await task；不要把两者统称为 await 锁。
  • WaitAsync(ct) 只取消该等待者；factory 获得 CancellationToken.None。200 ms 的上游重试不会撤销原始读，另一 pod 可以再读一遍。对共享加载设独立超时预算和应用停止 token，不绑第一个调用者；确认超时传到实际分页/SDK 调用。永不完成的 factory 会留住 inflight 条目。
  • 如果 factory 返回的是 IAsyncEnumerable<T> 而非已物化的一页/集合，缓存共享的可能只是序列对象，每次枚举仍可能再查 DDB。先核实生产 factory 的 T；这不是已证实的缺陷。
  • 同一字符串 key 应固定类型及语义；赢家决定 factory 和 TTL。Remove 只删已存值，进行中的旧加载仍可能写回。SizeLimit=条数不能约束等待任务/对象字节，容量拒写或驱逐会造成连续 miss。优先观察命中、加载、等待、驱逐与每次加载扇出，而不是先改锁。
05 / 方案比较

先获取基线，不把预热任务当作默认修复

v3：30 秒轮询只能争取“由谁发起”，不能提前于 SDK 的窗口强刷

若 API 调用频繁，请求常会比下一次 tick 更早跨过门槛；若后台先抢到，同实例的业务请求仍会等待它完成。启动时就取到 provider 对象也不代表已经拿到了有效凭证，首取可能仍需访问 agent。BackgroundService 不是专用线程池，对线程池饥饿、GC、CPU throttling 无隔离作用。[3] [4] [6]

若必须做 v3 对照：在服务组合根解析一次预期的可刷新 AWSCredentials，给实际使用的 AddAWSService 客户端选项设置这一个对象；后台从同一个 DI 注册取对象；不要每次 tick 解析链、另建 service provider/客户端、复制 ImmutableCredentials 或固化 SessionAWSCredentials。确认扩展/配置名、注册顺序及自建 client 旁路；装饰器的同步和异步入口都要代理。为该实例生成进程内随机编号，在构造与实际取用处比对，配合观察是哪一个实例发起了访问；仅记录类型或两次 GetRequiredService 相同不足以证明 DDB 也在用它。[5] [6]

默认链选择也可能因 profile、环境或显式配置而改变；不要把生产角色默默换掉。首次无凭证或必须刷新但端点失败时，核对的 v3 GenericContainerCredentials 会重试，最终异常可传回调用者，既不能假设无限重试，也不能保证回退到旧值。worker 要捕获非停机异常、带上限退避和 jitter、禁止重叠 tick、限速告警；不处置与客户端共用的 provider。区分 readiness 与 liveness，避免一次 agent 故障导致整组 pod 重启。[3] [4]

30 秒探测是主动干预而非中性测量；>100 ms 日志既可能只是等待别人的刷新，也会漏掉快速刷新和样本分母。记录所有时长的直方图，以及少量慢/失败/实际刷新事件。错开各 pod 的启动与轮询，保留功能开关和未预热对照组。

v4：在持续流量下优先试原生机制，不是定时保活

AWS issue #4024 记录第一版因可能提供过期凭证而回滚；PR #4100 重做预取和过期保护。仓库发布标签 4.0.129.0 对应 AWSSDK.Core 4.0.3.0，二者不是同一编号。[7] [8] [9]

Core 4.0.3.0 参考状态该请求的行为
有可用凭证、尚未到预取窗口返回现有凭证；没有流量也不会由此产生一个独立的定时任务。
进入预取窗口，尚在安全期一次调用触发后台加载；其他调用通常继续使用仍有效的旧凭证，同一实例避免重复启动后台刷新。
冷启动/长时间无流量/到安全边界需要前台取得有效凭证，仍可能等或报错。后台失败可再次尝试，不能永远发旧凭证。

该发布快照在保存状态时扣除默认 1 分钟安全缓冲，再对状态应用容器 provider 默认 15 分钟预取窗：真实剩余约 16 分钟开始有预取机会，约 1 分钟进入需等待区。不是整个 v4 的永久契约；核对所用包、provider 与参数。[10] [13]

决策：若证实前台刷新影响业务且能升级，在一组 pod 上只改成兼容的 v4 Core、DynamoDBv2、Setup 和仓储包组合，不叠加自建 worker。验证凭证链优先级、签名/授权、取消/重试、映射的空集合/null、分页和冷启动；不要把 v4 Core 硬塞给 v3 服务包，也不要以本地 net10 样例可编译代替生产兼容性。若高点不变或错误率升高，回滚镜像，继续沿非凭证时间段查。[9] [12]

06 / 验证手册

先用三个时间点切开这 1 秒

在真正执行查询的请求上记录：① factory 开始 → ② SDK 原有 GetCredentialsAsync 进入 → ③ 凭证 HTTP 开始。①–② 的延迟不应归给凭证锁；②–③ 的延迟仍需区分信号量等待、线程池调度、读 token 和先前失败的尝试。若在 ① 之前已慢，再查入口排队和缓存路径。

  1. 固定身份与分母。同一镜像先观察至少 3 个预测刷新周期；记录 UTC、pod/节点匿名标识、进程启动时间、版本、业务操作、成功/超时与尝试次数。跨 pod 用对齐后的 UTC 关联，进程内用单调 Stopwatch 记差。分别画每 pod 和全局合并 histogram 的 p95/p99 与慢请求数；区别上游首次、重试和服务端仍在运行的原请求。
  2. 只包住本来就会发生的调用。入口 → 缓存命中/创建/加入现有 flight → factory 开始 → 查询构造 → 实际读每页 → SDK 原有 provider.GetCredentials[Async] 开始/结束 → 凭证 HTTP attempt → DDB HTTP attempt → 返回。不要在 Query 前额外 GetCredentialsAsync 冒充探针，它会抢先刷新。用无配置改变的短时 runtime 诊断或在核对过版本的客户端/装饰器上计时真实入口；委托原 provider，保留凭证与异常语义。若无法观察 provider 内部，标为未知，不用两 span 的差值命名为锁等待。
  3. 识别谁在等谁。给每次真实 factory 创建一个短期 flight id；等待者以 trace link 关联，不为每个等待者虚构 DDB 子 span。provider 实例、调用起止、agent HTTP 的父 trace、成功及失败尝试、上次到期时刻要能对齐。Expiration 只记 UTC/剩余秒；取不到则标未知，不额外拉凭证。把 HTTP 客户端事件与 agent 端接收/响应分开，区分上网前和服务端处理。
竞争解释可区分的观测什么会削弱它
前台刷新排队同实例一个 owner 调 agent，多次 provider 调用区间与之重叠，释放后成批返回；预测窗反复对齐。provider 全程很短，或该秒落在 provider 入口之前。
线程池、GC、CPU 配额同 pod、同时间、无需 DDB 的可比异步接口也停顿；用 dotnet-counters / 短时 EventPipe 区分排队、worker 增长、GC 暂停区间；比对容器 CPU throttled time、节点负载。对照路由正常且实测停顿只在一个 flight；单个 CPU 或 GC 均值不足以排除。
缓存放大/仓储分页leader 慢、followers 多；或首个读页很快但慢在后续页；按页、AWS 操作、attempt 区分。快慢样本的 flight 扇出和页数相同、绝大部分差值只在真实取凭证段。
节点 agent、网络或重试同节点不同 pod 相关；查 agent 缓存/错误、token 文件读取、连接池、DNS（仅实际用主机名时）、TCP/TLS、早期失败和退避。agent 接收前慢而节点请求正常；连接建好后的快 span 不能排除先前失败。
DDB 或时间桶假象按表/操作比 CloudWatch SuccessfulRequestLatency、throttles、系统错误与 SDK 重试；查小时 cron、rollout、HPA、桶边界及每分钟样本数。DDB POST 及服务端都快，而延迟已由其上游的实测区间解释。AWS 服务端指标不含客户端排队。

对每个 trace 做耗时账本：provider_total − 与其重叠的凭证 HTTP 时间并集 是“尚未分解的 provider 时间”，不是“等锁时间”；不要叠加嵌套/并行 span。要进一步分解，可在测试镜像对完全相同 SDK tag在信号量前后、Generate 调度/开始、token 读取与各次 HTTP 调用打只读时间戳，或用 EventPipe 关联调度与暂停。[2] [3] [4] [11]

定案标准：多个窗口内，过期预测、同实例 owner/waiter、空白时长和受影响请求比例能闭合；随后单变量灰度让后台刷新取代前台等待，业务 >200 ms 占比与 p95 同时改善，错误/重试不升，且对照组仍复现。若只有刷新关联而主耗时在 Task.Run 开始前，应报告“刷新触发、调度放大”，而不是单报“凭证锁慢”。若对照也改善或样本太少，不判定成功。

只在权限受控的诊断系统保留 pod/trace 关联。不记录 token 文件内容、Authorization、AccessKey、SessionToken、原始 key、请求体或原始凭证响应；不把高基数键放进指标标签或 Pages。
