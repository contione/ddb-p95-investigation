同一 TraceId 下的两次请求尝试

两次尝试沿用同一 TraceId，Pod A 和 Pod B 都实际查询了 DynamoDB，没有从业务缓存返回结果。看瀑布图时，按各次尝试的入口 SpanId、父子关系与 Pod 区分分支，不把两边的时长相加。Pod A 的凭证请求之前约有 1 秒没有 span。上游没有等满这 1 秒：约 200 ms 超时后，它把重试发给了 Pod B。

02　两边各自发生了什么？

实线框：按你描述的 trace 观测到　·　虚线框：代码路径或待验证解释

Pod A · 首次尝试

  1. 请求进入服务
  2. 约 1 秒 · 内部未分段仓储 ToListAsync（hash key + range key）到 SDK 取凭证是需要分段计时的查询路径。各段耗时未知。
  3. /v1/credentials 响应很快
  4. POST DynamoDB

Pod B · 上游重试

  1. 超时后，重试落到另一个 Pod
  2. 未看到凭证 HTTP未看到访问凭证端点，并不影响实际发送 DDB 查询；凭证与业务查询结果是两回事。
  3. 直接 POST DynamoDB
  4. 本次重试 80–90 ms 完成

03　同一条 trace 里怎么定位空白？

空白发生在凭证 HTTP 之前，不等于整个空白都花在等凭证锁上。

  1. 仓储查询入口 → SDK 进入原有取凭证调用：如果这里慢，就先查仓储调用前缀和运行时调度；还没进入这次凭证调用。
  2. SDK 取凭证入口 → 凭证 HTTP 发出：如果这里慢，再区分信号量等待、刷新任务调度、token 文件读取以及先前失败的尝试。

查询入口按你补充的 ToListAsync 标注；没有据此假定底层一定是 Query、GetItem 或一定发生分页。波动的高分位数是总体指标，这张图只解释一组慢请求与重试。
